1//! Application API and ASP integration overview.
2//!
3//! # Local commands
4//!
5//! [`check`] evaluates source selected by [`CheckArgs`]. Its default selection compares
6//! current worktree changes with HEAD; `all` evaluates the entire supported source view.
7//! [`run_sense`] examines exact dependency changes selected by [`SenseArgs`]. Both commands
8//! print their result and return an error for blocking findings or unavailable coverage.
9//! [`run_workflow`] combines Verify, Sense, and required native providers with the resolved
10//! repository settings for post-edit, pre-commit, or CI.
11//! [`doctor`], [`status`], and [`rules`] provide read-only operational information.
12//!
13//! # Provider API
14//!
15//! [`ProviderProfile`] documents every bundled provider, including its prerequisites,
16//! command, supported scope, and execution boundary. Use [`serve_stdio_profile`] to start
17//! one provider identity, or run `opcore serve --stdio --profile <profile>`.
18//! [`render_provider_manifest`] produces the matching manifest after installation; its
19//! executable path and checksum bind the exact installed binary.
20//!
21//! Every provider implements ASP Core `check/1.0` over JSON-RPC 2.0, with one UTF-8 JSON
22//! object per line. The lifecycle is `initialize`, `initialized`, `check/evaluate`,
23//! `shutdown`, then `exit`. Cancellation uses `$/cancelRequest`. Evaluation cannot begin
24//! until the host's initialized grant permits it. Providers request exact immutable bytes
25//! through host `workspace/listTree` and `workspace/readBlob` callbacks.
26//!
27//! A `check/evaluate` assessment contains diagnostics, coverage, and evidence bound to the
28//! baseline, change digest, blobs read, effective configuration, and provider build.
29//! `introduced` compares public diagnostic fingerprints; `all` returns current findings.
30//! Providers never decide whether a change may be applied. The calling host owns decisions,
31//! policy authority, isolation, and receipts. Opcore's private local runner is advisory
32//! and does not issue an ASP adoption receipt.
33//!
34//! The complete request/response schemas, examples, and protocol specification are included
35//! in the repository and platform archive under `asp/`; they are the normative wire API.
36//! Hosts resolve repository and workflow settings and send the provider's effective
37//! configuration with each request. The provider validates and binds those settings.
38//!
39//! # Rust embedding
40//!
41//! This module is the executable's supported Rust boundary; internal parser and graph types
42//! are not a public library API. Asynchronous entrypoints require a Tokio runtime. For example,
43//! an outer host can select an identity without invoking a repository tool:
44//!
45//! ```no_run
46//! use opcore::api::{ProviderProfile, serve_stdio_profile};
47//!
48//! # async fn example() -> anyhow::Result<()> {
49//! serve_stdio_profile(ProviderProfile::Fast).await?;
50//! # Ok(())
51//! # }
52//! ```
